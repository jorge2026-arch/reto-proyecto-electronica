# Constitución del Backend

## 1. Propósito

Este documento define las decisiones técnicas, arquitectónicas y funcionales para construir el backend de la tienda de electrónica.

El backend expondrá una API REST para autenticar administradores y administrar los productos almacenados en PostgreSQL.

## 2. Stack tecnológico obligatorio

| Área | Tecnología | Decisión |
|---|---|---|
| Lenguaje | TypeScript | Tipado estático y mejor mantenibilidad. |
| Capa HTTP | Hono | Framework ligero compatible con Web Standards y Vercel. |
| Runtime | Node.js en Vercel | Necesario para utilizar `bcrypt` de forma compatible. |
| Base de datos | PostgreSQL | Motor utilizado por el esquema existente en `db/`. |
| Autenticación | JWT | Autenticación de las rutas privadas de la API. |
| Contraseñas | `bcrypt` | Hash de contraseñas con exactamente 8 saltos. |
| Validación | Zod | Validación en tiempo de ejecución de cuerpos, parámetros y consultas. |
| Middleware Zod | `@hono/zod-validator` | Integración de Zod con Hono. |
| Pruebas | Vitest | Pruebas unitarias e integración. |
| Calidad | ESLint y Prettier | Formato y calidad consistente del código. |

## 3. Arquitectura

Se utilizará una arquitectura de tres capas, adaptada al patrón MVC:

```text
Rutas y controladores
          ↓
Servicios de negocio
          ↓
Repositorios y PostgreSQL
```

### 3.1 Rutas y controladores

- Definen los endpoints HTTP de la API.
- Reciben solicitudes y construyen respuestas.
- Aplican validación con Zod.
- Aplican autenticación JWT en las rutas privadas.
- No contienen consultas SQL ni lógica de negocio compleja.

### 3.2 Servicios

- Contienen las reglas de negocio.
- Gestionan el inicio y cierre de sesión.
- Ejecutan las operaciones CRUD de productos.
- Coordinan repositorios, hash de contraseñas y generación de tokens.
- No deben depender directamente de objetos específicos de Hono.

### 3.3 Repositorios

- Encapsulan el acceso a PostgreSQL.
- Utilizan consultas parametrizadas.
- No reciben datos sin validar.
- Devuelven entidades o resultados definidos por la aplicación.

### 3.4 Estructura de carpetas esperada

```text
backend/
├── spec-kit-backend/
│   └── 1.constitucion.md
└── src/
    ├── app.ts
    ├── config/
    ├── routes/

    ├── services/
    ├── repositories/
    ├── schemas/
    ├── middleware/
    ├── types/
    ├── db/
    └── utils/
```

## 4. Compatibilidad con Hono y Vercel

Hono es compatible con Vercel sin una configuración especial de adaptador. La aplicación deberá exportar la instancia de Hono como exportación `default` desde uno de los puntos de entrada reconocidos, preferentemente:

```text
backend/src/index.ts
```

Ejemplo mínimo:

```ts
import { Hono } from 'hono'

const app = new Hono()

export default app
```

En Vercel, las rutas de Hono se ejecutan como Vercel Functions. El desarrollo local se realizará con:

```bash
vc dev
```

La aplicación no utilizará `serveStatic()` para archivos públicos en Vercel. Los archivos estáticos, si fueran necesarios, deberán ubicarse en `public/`.

### 4.1 Runtime

Se debe utilizar Node.js en lugar de Edge Runtime porque `bcrypt` puede depender de componentes nativos de Node. No se deberán importar APIs exclusivas de Node en módulos que deban ejecutarse en Edge.

### 4.2 Base de datos en Vercel

Las funciones serverless pueden crear múltiples instancias. La conexión PostgreSQL deberá:

- Usar una URL almacenada en `DATABASE_URL`.
- Reutilizar el pool de conexiones entre invocaciones cuando sea posible.
- Mantener un límite razonable de conexiones.
- Usar un proveedor PostgreSQL compatible con conexiones serverless.
- Evitar crear un pool nuevo por cada solicitud.

Se utilizará `pg` para una conexión PostgreSQL tradicional. Si el proveedor elegido es Neon, podrá sustituirse por `@neondatabase/serverless`.

## 5. Dependencias

### 5.1 Dependencias de producción

```bash
npm install hono zod @hono/zod-validator bcrypt pg
```

El middleware JWT integrado de Hono será la opción preferida mediante:

```text
hono/jwt
```

No se añadirá otra biblioteca JWT salvo que una necesidad concreta lo justifique.

### 5.2 Dependencias de desarrollo

```bash
npm install -D typescript @types/node @types/bcrypt vitest eslint prettier
```

## 6. Seguridad

### 6.1 Contraseñas

- Nunca se almacenarán contraseñas en texto plano en producción.
- El registro o actualización de contraseñas deberá utilizar `bcrypt.hash(password, 8)`.
- La autenticación deberá verificar con `bcrypt.compare`.
- El administrador inicial se inserta con un hash bcrypt generado con 8 saltos.

### 6.2 JWT

- El token se emitirá únicamente después de validar las credenciales.
- Las rutas privadas exigirán `Authorization: Bearer <token>`.
- El secreto se obtendrá de `JWT_SECRET`.
- El token tendrá expiración configurada mediante `JWT_EXPIRES_IN`.
- El payload incluirá como mínimo el identificador del administrador y su usuario.
- No se incluirán contraseñas ni información sensible en el payload.

### 6.3 Cierre de sesión

JWT es stateless. El endpoint de cierre de sesión confirmará la operación y el cliente deberá eliminar el token.

Si posteriormente se requiere invalidación inmediata de tokens, se añadirá una lista de revocación en PostgreSQL o Redis.

## 7. Variables de entorno

```env
DATABASE_URL=
JWT_SECRET=
JWT_EXPIRES_IN=1h
NODE_ENV=development
```

Las variables reales no se almacenarán en el repositorio. Se deberá incluir un archivo `.env.example` sin secretos.

## 8. Modelo de datos

El backend utilizará las tablas existentes:

### Administrador

- `identificador`
- `usuario`
- `contrasena`

### Producto

- `identificador_producto`
- `modelo_producto`
- `precio`
- `stock`
- `categoria`

Las reglas de integridad también están definidas en los scripts SQL de `db/`.

## 9. Requerimientos funcionales

### RF-01: Inicio de sesión del administrador

El sistema deberá permitir que un administrador inicie sesión utilizando usuario y contraseña.

```http
POST /api/auth/login
```

Respuesta exitosa: token JWT y datos públicos del administrador.

### RF-02: Cierre de sesión del administrador

El sistema deberá permitir cerrar la sesión del administrador autenticado.

```http
POST /api/auth/logout
```

### RF-03: Registrar producto

Solo un administrador autenticado podrá registrar productos.

```http
POST /api/products
```

### RF-04: Actualizar producto

Solo un administrador autenticado podrá actualizar un producto existente.

```http
PATCH /api/products/:id
```

### RF-05: Eliminar producto

Solo un administrador autenticado podrá eliminar un producto existente.

```http
DELETE /api/products/:id
```

### RF-06: Listar productos

El catálogo podrá consultarse públicamente. La autenticación no será necesaria para operaciones de lectura.

```http
GET /api/products
```

La respuesta deberá permitir paginación para evitar consultas excesivamente grandes.

### RF-07: Filtrar productos

El listado público deberá permitir filtrar por modelo, categoría o ambos criterios.

```http
GET /api/products?modelo=Galaxy&categoria=celular
```

Las categorías válidas serán:

```text
celular, laptop, monitor, teclado, mouse, audifonos
```

## 10. Validaciones

Zod deberá validar:

- Usuario con máximo 15 caracteres.
- Contraseña con máximo 60 caracteres.
- Precio mayor que cero.
- Stock mayor o igual que cero.
- Categoría perteneciente al conjunto permitido.
- Identificadores numéricos positivos.
- Parámetros de filtro y paginación.

Todas las consultas SQL deberán utilizar parámetros para evitar inyección SQL.

## 11. Respuestas HTTP

La API utilizará respuestas JSON consistentes:

```json
{
  "success": true,
  "data": {}
}
```

Los errores utilizarán el formato:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Los datos enviados no son válidos"
  }
}
```

Como mínimo se utilizarán:

- `200 OK`
- `201 Created`
- `204 No Content`
- `400 Bad Request`
- `401 Unauthorized`
- `404 Not Found`
- `409 Conflict`
- `500 Internal Server Error`

## 12. Fases de implementación

### Fase 1: Inicialización

- Crear el proyecto TypeScript.
- Configurar `package.json` y `tsconfig.json`.
- Instalar Hono y las dependencias base.
- Configurar el punto de entrada compatible con Vercel.
- Crear `.env.example`.

### Fase 2: Persistencia

- Configurar PostgreSQL.
- Crear el pool de conexiones.
- Implementar repositorios de administrador y producto.
- Verificar compatibilidad con las tablas y restricciones de `db/`.

### Fase 3: Validación

- Crear esquemas Zod.
- Configurar `@hono/zod-validator`.
- Validar cuerpos JSON, parámetros de ruta y query strings.
- Crear respuestas uniformes para errores de validación.

### Fase 4: Autenticación

- Implementar comparación con bcrypt.
- Implementar generación y validación JWT.
- Crear middleware de autenticación.
- Implementar login y logout.
- Proteger las rutas de productos.

### Fase 5: Productos

- Implementar registro.
- Implementar actualización.
- Implementar eliminación.
- Implementar listado paginado.
- Implementar filtros por modelo y categoría.
- Mantener públicas las operaciones `GET` y protegidas las operaciones `POST`, `PATCH` y `DELETE`.

### Fase 6: Manejo transversal

- Configurar CORS.
- Crear manejador global de errores.
- Añadir logs seguros.
- Evitar exposición de contraseñas y secretos.
- Añadir headers de seguridad.

### Fase 7: Pruebas

- Probar credenciales válidas e inválidas.
- Probar tokens ausentes, inválidos y expirados.
- Probar validaciones de productos.
- Probar operaciones CRUD.
- Probar filtros individuales y combinados.
- Probar errores de base de datos.

### Fase 8: Despliegue

- Configurar variables de entorno en Vercel.
- Ejecutar localmente con `vc dev`.
- Verificar el despliegue como Vercel Function.
- Probar entornos Preview y Production.
- Revisar conexiones PostgreSQL y límites serverless.

## 13. Criterios de aceptación

- La API se inicia correctamente con Node.js.
- Hono se exporta como `default` y es desplegable en Vercel.
- Las rutas privadas rechazan solicitudes sin JWT válido.
- Las contraseñas nuevas utilizan bcrypt con 8 saltos.
- Los datos inválidos son rechazados mediante Zod.
- Las operaciones CRUD funcionan contra PostgreSQL.
- Los filtros por modelo y categoría funcionan de forma independiente y combinada.
- No se exponen contraseñas, hashes ni secretos en las respuestas.
- Todas las pruebas automatizadas pasan antes del despliegue.
